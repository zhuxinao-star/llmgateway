# LLM Gateway 部署指南

本地大模型 API 网关：聚合多家 LLM 供应商（OpenAI 兼容 / Anthropic 协议），对外提供统一的 OpenAI 兼容接口与 Anthropic 原生接口，内置智能路由（优先级 / 速度学习 / 熔断 / 429 冷却与限流学习撤席 / 预算 / 多 Key 轮转）、语义路由、上下文窗口过滤、**上下文自动压缩**（长会话 Agent 专用）、对冲竞速、虚拟模型分组、用量统计。Java 21 + Spring Boot 3.3.5 + SQLite，单机免安装，无外部依赖。

---

## 1. 目录结构

**克隆下来就是这个样子**（仓库根目录＝应用目录，即有 `pom.xml` 的那一层，下面统称「项目根」）：

```
<项目根>\
├── pom.xml                      Maven 工程定义
├── src\                         源码
├── config\
│   ├── config.example.yaml      配置模板（无密钥）
│   └── config.yaml              你填的运行配置（含密钥，已被 .gitignore 排除）
├── scripts\                     Windows 脚本：_env / start / stop / restart / status / build / doctor
├── target\                      构建产物 llmGateway.jar（不入库）
├── data\                        运行库 llm-gateway.db（脚本默认落这里，不入库）
├── logs\                        app.log（系统）+ gateway.log（每请求一行，不入库）
└── docs\                        部署指南 / 管理页使用指南 / 目录结构说明
```

作者在开发机上把工具链和数据挪到了项目根的同级分区（`tools\` 便携 JDK+Maven、根级 `data\`、`logs\`、`dev\` 无源码部署包），这些**不随仓库发布**；脚本不依赖那种布局，只要按第 2 节的规则找到 JDK/Maven 就行。

## 2. 环境要求

- **JDK 21 或更新**（Spring Boot 3 用虚拟线程，17 也跑不起来）——这是唯一的硬要求
- **Maven** 只在你要自己构建 jar 时需要（发布的是源码，所以首次要构建一次）；只想跑别人的 jar 就不用装
- **Windows**：`scripts\` 是 bat。Linux/Mac 直接 `mvn -q package -DskipTests` + `java -jar target/llmGateway.jar`（工作目录＝项目根）
- 磁盘：约 200MB（源码+构建产物）；内存 256MB 起
- 无需数据库、无需中间件，SQLite 嵌入式

## 3. 首次部署：脚本路径规则 + 四步跑起来

### 第 0 步：`scripts\doctor.bat`（先跑这个）

它把脚本**实际找到**的东西逐条打出来：项目根、配置、jar、日志目录、库文件、JDK 目录与版本、有没有 javac、Maven、端口从哪来、端口现在是不是已被占用。改路径不用猜——改完再跑一遍确认。

### 脚本的路径规则：下载后要改什么

**基本什么都不用改。** 所有路径只在一个地方解析：`scripts\_env.bat`（其余脚本第一行都 `call` 它）。规则：

| 找什么 | 规则 |
|---|---|
| 项目根 | `scripts\` 的上一级（由脚本自身位置推出），并检查那里有 `pom.xml`；没有就报 `[layout error]` 退出 |
| JDK | `GW_JDK` → `<项目根>\tools\jdk-*` → `JAVA_HOME` → PATH 上的 `java`，然后验版本 ≥ 21 |
| Maven | `GW_MVN` → `<项目根>\tools\apache-maven-*\bin\mvn.cmd`（同级有 `settings.xml` 时自动带 `-s`）→ PATH 上的 `mvn` |
| 日志 / 库 | `GW_LOG_DIR` / `GW_DB_PATH`；没设则 `GW_BASE\logs`、`GW_BASE\data`；`GW_BASE` 也没设就是项目根 |
| 端口 / 网卡 | `GW_PORT` / `GW_HOST`；没设则读 `src\main\resources\application.yaml` 的 `server.port` / `server.address` |
| jar / 运行配置 | `<项目根>\target\llmGateway.jar`、`<项目根>\config\config.yaml`（固定，不可覆盖） |

克隆到 `D:\anywhere`、`C:\Users\me\Downloads\llmgateway` 都不用动脚本，路径里有空格括号也无碍（作者自己用的就是 `D:\model switch`）。要动手的只有两种情况：

1. **机器上没有 JDK 21 / Maven**：设 `GW_JDK` 指到 JDK 目录（不是 `bin`），或把便携 JDK 放进 `<项目根>\tools\jdk-21.x.x\`；Maven 同理设 `GW_MVN` 指到 `mvn.cmd`。
2. **想换数据/日志位置，或 8317 被占用**：设 `GW_BASE`（一次挪走 `data\` 和 `logs\`），或单独设 `GW_DB_PATH` / `GW_LOG_DIR` / `GW_PORT` / `GW_HOST`（这两项比 `GW_BASE` 优先）。

变量在同一个命令行窗口里设好再调用脚本，脚本不写注册表、不改你的文件：

```bat
cd /d D:\somewhere\llmGateway
set GW_JDK=D:\java\jdk-21
set GW_BASE=E:\llm-data
set GW_PORT=9000
scripts\doctor.bat        & rem 先确认它读到的值
scripts\build.bat
scripts\start.bat
```

**端口这条有坑，说明白**（`doctor.bat` 里也会明说）：

- 真正决定监听端口的是 `src\main\resources\application.yaml` 的 `server.port`（默认 8317）。
- 你设了 `GW_PORT`，脚本会给 JVM 注入 `-Dserver.port=<GW_PORT> -Dserver.address=<GW_HOST>`；系统属性优先级高于 jar 里的 yaml，所以**确实生效**（本机实测：`GW_PORT=18317` 时日志出现 `http-nio-127.0.0.1-18317`，`/api/overview` 在 18317 返回 200，`stop.bat` 按 18317 停得掉）。
- `config\config.yaml` 里的 `server: bind/port` **不控制监听**，只被用来打印启动那一行"服务在哪"的日志（`com.gw.Startup`），改它没效果。要长期改端口就改 `application.yaml` 再 `build.bat`。
- 想让局域网其它机器访问：`set GW_HOST=0.0.0.0`（同时把 `gateway-keys` 换成强随机值，见第 8 节）。

**要二次开发脚本时的两条硬规矩**：

- `.bat` 正文**只能用 ASCII**，注释和提示语都别写中文。控制台代码页 936 会把 UTF-8 中文读成乱码字节，其中某些字节含括号，会直接把 cmd 的解析打断。
- 别把 `for /f ... in ('...')` 塞进 `( ... )` 块里，也别在块里回显带 `(` `)` 的值（比如 `Java(TM)`）。路径和版本串里出现括号就会报"此时不应有 ..."。所以脚本里的错误分支一律用 `goto` 标签平铺。

### 第 1 步：构建

执行 `scripts\build.bat`，成功时末尾显示：

```
[OK] <项目根>\target\llmGateway.jar
```

服务正在跑时 jar 被占用，脚本会先拒绝并提示你跑 `scripts\stop.bat`。构建要联网拉 Maven 依赖（首次约几百 MB，走你在 `settings.xml` / `~/.m2` 里配的仓库）。

### 第 2 步：创建配置

复制模板并填写你自己的供应商 Key（都在项目根的 `config\` 下）：

```bat
copy config\config.example.yaml config\config.yaml
```

最小可用配置（其余项保持默认）：

```yaml
server:
  bind: 127.0.0.1
  port: 8317              # 注意：这两项只决定启动日志打什么，不控制实际监听（见第 3 节端口那条）

gateway-keys:
  - "my-gateway-secret-001"    # 网关本地鉴权 Key：接入工具填这个，自己起一个即可

providers:
  - id: myprovider
    name: 我的供应商
    baseUrl: https://api.example.com/v1     # 供应商的 OpenAI 兼容地址
    protocol: openai                         # openai 或 anthropic
    priority: 1                              # 数字小者优先
    defaultCostTier: free                    # free/low/standard/premium（影响路由打分）
    # proxy: http://127.0.0.1:7897           # 可选：该供应商出站走本地代理（Clash 常见 7890/7897），不填=直连
    channels:
      - id: main
        apiKey: "sk-xxxxxxxxxxxxxxxx"        # 你在供应商处申请的 Key
    static-models: ["model-a", "model-b"]    # 该供应商要用的模型清单

groups:
  - name: free-fast
    autoAll: true       # 自动组：动态包含所有供应商的全部手工模型，工具侧只填这一个名字
```

> 说明：也可以先启动后，完全在管理页界面上点出来（推荐），见《管理页使用指南.md》第 2 节。
>
> `proxy` 是**按供应商**生效的 HTTP 代理：转发、拉上游模型清单、查余额三条出站路径共用同一个客户端工厂（`com.gw.util.ProviderClients`），所以配了就三条路一起走，不会出现"转发生效、查清单仍失败"。Java 的 HttpClient **不读 Windows 系统代理**，Postman/浏览器能通不代表网关能通——被 CDN 边缘拦截的供应商必须显式填这一项，见第 7 节。

### 第 3 步：启动

```bat
scripts\start.bat
```

脚本自己开一个窗口跑服务（不占你的命令行），并回显它把服务放在哪：

```
[starting] http://127.0.0.1:8317/ui/index.html
[java]     <它找到的 JDK 目录>
[logs]     <项目根>\logs\app.log
[db]       <项目根>\data\llm-gateway.db
[port]     8317 from application.yaml
```

启动前按顺序过六道检查，任何一道不过就直接说什么并退出（不会默默起个半死进程）：`scripts\` 是否紧贴项目根、有没有 JDK、JDK 是否 ≥21（会打出实测版本号和它在哪找到的）、有没有 `config\config.yaml`、有没有 jar（提示先 `build.bat`）、端口是否已被占用（提示"已在运行"并原样退出）。

浏览器打开管理页：

```
http://127.0.0.1:8317/ui
```

### 第 4 步：日常运维

```bat
scripts\status.bat          & rem 探活：打 UP HTTP=200 或 DOWN（没有 /api/health，用 /api/overview）
scripts\status.bat log      & rem 看 app.log 最后 30 行
scripts\stop.bat            & rem 按端口找进程停掉
scripts\restart.bat         & rem 停 → 起 → 状态
```

`stop.bat` 只按端口定位进程，绝不会误杀你机器上别的 java 进程。

## 4. 接入工具（Agent / 客户端）配置

所有支持自定义 OpenAI 接口地址的工具都能接：

| 配置项 | 值 |
|---|---|
| Base URL | `http://127.0.0.1:8317/v1` |
| API Key | 你在 `gateway-keys` 里设的值（如 `my-gateway-secret-001`） |
| 模型名 | 组名（如 `free-fast`）、具体模型名、或 `供应商id/模型名` 强制点名 |

- OpenAI 格式端点：`POST /v1/chat/completions`、`GET /v1/models`
- Anthropic 原生端点（Claude Code 等直连用）：`POST /v1/messages`，鉴权支持 `x-api-key` 或 `Authorization: Bearer`

Claude Code 对接示例：

```bash
export ANTHROPIC_BASE_URL=http://127.0.0.1:8317
export ANTHROPIC_AUTH_TOKEN=my-gateway-secret-001
claude --model free-fast
```

请求了不存在的模型名会自动回落到 `free-fast` 组，所以工具里只填 `free-fast` 一个名字就永远可用。

## 5. 运行机制速览（帮助你决定怎么配置）

**选路打分**

- **优先级 priority**：数字越小越先被尝试，失败自动按顺序换下一家
- **打分**：优先级 × 健康度（连续失败降权）× 首字速度（EWMA，越用越准）× 吞吐速度（出 token/秒 EWMA）× 费用档 × 语义类别匹配
- **语义路由**：给模型打"擅长类别"标签（code/doc/analysis/general），请求内容自动判类，类别命中的模型加分——写代码的请求优先发给会写代码的模型
- **熔断**：同一供应商×模型连续失败 3 次 → 冷却 60s 起指数退避；429 → 该 Key 冷却 30s；429 配额耗尽（insufficient_quota）→ 该 Key 冷却 10 分钟
- **对冲竞速**（`defaults.hedgeDelayMs`，默认 2500）：主选 2.5s 没吐首字时并发次选竞速，谁先出字用谁、输家掐断（几乎不耗 token）。陪跑只挑免费档；输入超过 `hedgeMaxContextTokens`（默认 10K token）的大请求禁用对冲，避免双倍消耗 TPM
- **多 Key 轮转**：同供应商配多把 Key 时严格一单一单轮流分摊（刚用过的排后），一把限速另一把自动顶上
- **永不空手**：候选穷尽尝试（最多 6 家）+ 全熔断也强制放行一家探测 + 未知模型回落 free-fast

**大上下文治理（Agent 工具长会话必备）**

- **上下文上限 contextWindow**（路由条目字段）：给模型配上限（如 128000），请求输入超限的模型直接跳过，不再白烧尝试次数——免费模型窗口参差不齐（64K~128K），大请求只发给装得下的
- **上下文自动压缩**（`defaults.contextCompressThresholdTokens`，默认关闭）：输入超过阈值时，网关先把历史压成摘要再转发——system 提示全保留、最近 `keepRecentMessages`（默认 10）条原文保留、其余历史由压缩模型生成"继续干活"用的摘要。**滚动缓存**：同一工具的会话只压缩新增部分（历史前缀哈希校验），后续每轮秒级完成。压缩模型建议配组名（如 `free-fast`）：全家档免费候选自动轮转 + **费用守卫**（组名配置下非免费候选一律跳过，免费政策变更也不产生账单）。压缩失败自动降级原样转发，永远不影响请求成功率。响应头 `X-Gateway-Context-Compressed: true` 标记本次已压缩
- **大请求不污染速度评分**：输入超 10K token 的请求，其首字时延不计入 EWMA（预填充慢不等于模型慢）
- **无样本压档**：新模型（无历史数据）不给乐观默认分参与跨档竞争，防止"没历史包袱"的付费模型反超有真实速度数据的免费模型

**按渠道关思考**（推理模型兼容）

部分免费推理模型默认开思考，Agent 小 max_tokens 请求会"只思考不回答"。网关按渠道注入对应的关思考参数（实测各家开关不同），用户请求显式携带思考参数则尊重不覆盖。

- 供应商字段 `thinkingMode`：`auto`（默认）＝只对该家落在网关内置名单里才注入关思考；`disable`＝该家一律注入关思考（openai 协议才注入，anthropic 协议家不碰）。内置名单（sensenova / deepseek / tokenrouter）是历史包袱，**新渠道不用再往里加**——遇到"默认开思考"的家，管理页供应商表单里把"思考模式"选成"一律关思考"即可。AMD 实测不认这类开关，永不注入
- **撞墙自愈**：`auto` 下若该家因为默认开思考而拒绝请求（400 `reasoning_content ... must be passed back`），网关会自动关思考重发一次，日志打 `[思考回传]` WARN；重发仍失败则回吐原始 400，不掩盖真实错误
- **Anthropic 入口回填**：claude-code 这类客户端会把思考块（`thinking`）回传给网关，此前直接丢弃，导致"历史里有 tool_calls 但没 reasoning_content"→ 默认开思考的上游 400。现在思考块回填成 `assistant.reasoning_content` 随消息带上游，思考可以一直保持开启（实测优先于关思考自愈）
- 该错误单独成类 `REASONING_PASSBACK`（不是"上下文超长"也不是超时），处置与 CONTEXT_TOO_LONG 同级：只留痕，不冷却 Key、不推熔断——网关能治的问题不该把一家好渠道打出候选池

**预算**

- 可给供应商/Key/模型配 `dailyTokenLimit`，当日超限自动避开（次日重置）

**Key（渠道）归因**（一家多把 Key 时判断"是这家慢，还是这把 Key 被限流"）

- 每次请求把实际使用的渠道 id 落在 `request_log.channel_id`（老库启动时一次 `ALTER TABLE` 探针式迁移，无新索引：SQLite 只有一个写连接，为按 Key 查加索引会给转发链路添写放大）；`logs\gateway.log` 的转发行同时带 `key=<渠道id>`
- 统计侧：`GET /api/usage-by-key?from=&to=[&providers=][&clients=][&models=]` 按 供应商×模型×Key 聚合（请求/成功/失败/撞429/输入输出Token/TTFT中位），失败与 429 的口径与供应商×模型明细、路由判限流完全同源，不另立一套
- **`channel_id` 为空＝归属功能上线前的历史请求**，一律单列成"上线前无归属"，不猜、不摊给任何一把；被网关侧拒绝的行（`provider_id='-'`）不进这张表
- `今日 N 次 · M tok`（供应商页每把 Key 行、按 Key 表的"今日Token/预算"列）来自 `PolicyService` 的**内存日计数器**，重启清零——所以它和窗口统计可能不一致，界面已标"实时运行值"。provider×model 与 provider×Key 两个维度的请求数在同一处递增，不会出现"token 有数、次数为 0"的自相矛盾
- `usage_daily` 主键仍是 (day, provider_id, model, client)，**没有**为 Key 拆维度：改主键要动迁移与所有下游读方，收益却能用 `request_log` 现算替代

**评分与分摊的可观测性**（管理页"评分与分摊"，见《管理页使用指南》2.6）

- **速带分摊抽签**（2026-10-12 改口径：**速度只决定谁先入座（排队），不决定"一共几个座"；进席后接几成流量只由偏好决定**）：候选按综合分排序后，前 N 个**模型**（按模型去重，同模型多把 Key 合占一席）组成抽签席，席内权重 `√(偏好分/最高偏好分)` 归一化成份额，随机抽一席置顶——所以"分数第一"不必每次都被选中，这是防单点的设计。`偏好分 = 综合分 ÷ 两个速度因子`（**首字 S 与出字 T 都除掉**）：同一席内的家按定义就是"速度相差不是很大"，份额里再除一次速度等于罚两遍，会让最快的家照样吃光流量；早前只除 S 时，吞吐差 8 倍的家仍能把流量吸走。开关与参数：`defaults.loadShare`（默认开）、`defaults.shareBandSize`（代码默认 3 席）、`defaults.shareSlowTtftMs`（**绝对**慢门槛，实测首字中位超过它完全不进席，代码默认 6000，本机已调到 14000）、`defaults.shareSpeedTieRatio`（**相对**并列带倍率，默认 3）、`defaults.shareMinSeats`（**席位下限**，代码默认 3，0=关闭）；只在 `auto`/`priority` 策略、且非 critical 请求时抽签
- **供应商两道封顶**（2026-10-12 新增，回答"席位按模型发，一家几个模型就吃光"）：`defaults.shareProviderSeatCap`（**甲·席位封顶**，代码默认 2，0=不限）——一家占满 N 席后同家排名更后的模型撤席（`BAND_PROVIDER_SEATS`），撤的仍只是抽签资格，兜底顺序里还在；`defaults.shareProviderCapPct`（**乙·份额封顶**，代码默认 0.35，0=不限）——一家**应得份额**合计不超过它，超出部分按权重**确定性回灌**给未达线的家（同输入同结果）。有效线＝`max(此值, 1÷当前占席家数)`：只有两家时不可能都 ≤35%，自动放宽到均分线，避免"封顶后加起来不到 100%"。判读口径：**实际占比**临时超线是合法的（别家冷却/撤席时量必然涌过来），**应得份额**长期超线才说明封顶没咬住，而刚改完参数时多半是样本早于改动，等新窗口过去即可
- **优先级与份额的换算**（配置调参用）：`P = 40/(1+优先级×5)`，0 级 vs 1 级是 6 倍分，但份额是 `√(分数比)` ⇒ 实际约 **2.45 倍**；1 级 vs 2 级只差 **1.35 倍**。所以"差一档就吃光"是错觉，真吃光是速度档/健康档叠加或席位被一家占满——先看这两处，再动封顶
- **应得份额的均值口径**（`RankTraceStore.observeShare`）：分母统一用窗口内**"有席的决策数"**，模型级与供应商级共用同一个分母，所以供应商列合计恒为 100%。按"各自出现过的次数"取均值再相加会算出 169% 这种不可能的数（旧实现踩过，界面"供应商汇总"那一层尤其明显）；无席决策对"谁该接几成"没有表态，不进分母，但仍计入"未进抽签席的原因"
- **并列带判的是什么**：绝对门槛跨场景（组里全是 20s 档时形同虚设，全是 300ms 档时又误杀 3s 的家），所以再加一条 `实测首字 > max(本组最快×shareSpeedTieRatio, 本组最快+3000ms)` 就不进"严格带"——取宽松侧，`SHARE_TIE_MIN_SPREAD_MS=3000` 保证亚秒级差异一律视为并列（229ms 与 900ms 不该分高下）。本次门槛随决策快照回传，界面沙盘顶部恒显"本次并列带门槛 Xms（本组最快 Yms×倍率，取宽松侧）"
- **席位下限（2026-10-14 补，回答"参数调了几轮还是只怼一两家"）**：并列带是**排队**用的，不是用来砍席位池的。本机实测：组里有一发 872ms 的快模型时，3872ms 的门槛把 9 家配置只剩 2 家在带内——抽签席最多在两家里轮换，其余家**永远拿不到流量 → 攒不出新的实测首字 → 那个估到的慢值永远推不翻**，是个自锁的负反馈。所以加了不变量：带内的家不足 `defaults.shareMinSeats`（默认 3，0＝关闭退回"速度说了算"）时，把带外"只因并列带被排后"的家按实测首字从快到慢**放宽补席**，补到下限或撞上限为止。三条边界（`ShareSeatFloorTest` 逐条钉住，跑法见《目录结构说明》的 `run-unit-tests.bat`）：① 补的只是抽签席，份额仍只由偏好分算；② 补席越不过硬门槛——绝对慢阈值、近期/慢性撞限流、同家席位封顶、无可用 Key 都照旧挡（带外最快的那家如果是被同家封顶挤掉的，也不会靠补席绕过）；③ 上限是 `bandCap = max(2, shareBandSize)`，下限不会把带宽撑大。回传字段 `seatFloor/seatsStrict/seatsRelaxed`，界面显示"本轮 N 家带内＋M 家放宽补席"
- **撤席的七种原因**（界面"未进抽签席的原因"恒显计数，代码里是 `PolicyService.BAND_*`）：`BAND_DUP_KEY` 同模型重复 Key 合占席 / `BAND_SLOW` 实测首字超绝对门槛 / `BAND_REL_SLOW` 比本组最快慢出并列带且补完席仍轮不到 / `BAND_VERY_SLOW` 极慢样本累计到门槛 / `BAND_RATE_LIMIT` 该家此刻在撞限流 / `BAND_CHRONIC_LIMIT` 该家长期撞限流 / `BAND_PROVIDER_SEATS` 该家已占满席位上限。撤席只撤"抽签资格"，候选仍留在兜底顺序里，其它家不可用时照样能服务
- **限流怎么进评分**（`AdaptiveRateLimiter`，三层）：
  - **瞬时层**降权按**渠道**：`限流压力 L = min(1−0.8×窗口压力, 1−0.65×撞墙密度)`，地板 0.2。窗口压力＝当前 60s 用量离"该 Key 学到的限流上限"有多近；撞墙密度＝近 5 分钟（`LIMIT_DENSITY_WINDOW_MS`）真吃了几个 429，4 次即满档（`DENSITY_FULL_LIMITS`）。只有窗口压力会漏——撞完一轮流量掉下去、压力归零、因子回到 1.0，于是又被抽中又立刻 429；密度样本滑出窗口即自动衰减，不需要人工复位，也不连坐同一家其它 Key
  - **瞬时撤席**按**家**：近 5 分钟撞限流 ≥3 次（`BAND_GATE_MIN_LIMITS`）且该家最紧的那把 Key 学到的额度 ≤5 次/分（`TIGHT_CEILING_REQ_PER_MIN`）→ 该模型不占抽签席。额度宽的家偶发几次不算
  - **慢性层**读**请求日志**（2026-10-12 新增，`chronicRateWindowMinutes` 默认 60 分钟、`chronicRateMinSamples` 默认 8、`chronicSeatBlockRatio` 默认 0.3）：按真实流量算每家的 429 占比，占比达撤席线且样本够 → 不占席（`BAND_CHRONIC_LIMIT`），未达线按同一条满罚刻度线性降权（达线 ×0.2、半线 ×0.6）。这一层由 60s 快照调度刷新、**启动时先刷一次**（`Startup.bootstrap`），所以重启不再失忆；样本不足或没撞过墙一律 ×1.0，"不罚未知"。手动"重新学习"（`reset`）会连慢性层一起清
  - **为什么还要第三层**：前两层是**内存态**，只记得最近这波，重启即清零——实测重启当天 sensenova 又连吃两发 429，因为网关"忘了"它天天撞墙。慢性层的数据源是 `request_log`，天然跨重启
- **速度样本自己会过期**（同批修）：① 流式转发的首字按**真·首字**计（旧实现记在"首个 chunk 到达之后"，实测出现 `ttft=1ms total=29110ms` 这种伪样本，把模型钉成"极快"）；② 回填样本与记录都设下限 `TTFT_ARTIFACT_FLOOR_MS=50`，低于它的一律当测量伪影丢掉；③ 跨重启恢复的中位数带时间戳 `medianTs`，超过 `RESTORED_MEDIAN_FRESH_MS`（3 小时）就回库重取，不再"上周一次抽风永久把模型钉在慢门槛外"；④ 回填查询排除 `probe/selfcheck/reconcile` 三类内部流量，且模型名按大小写归一匹配
- **运行时快照的键必须归一**（同批修的两个 bug）：`runtime_snapshot` 的 `channel_id` 用 `\u0001` 做命名空间标记，旧实现每重启多攒一个，Key 级冷却跨重启永远匹配不到（实测 858 行脏快照）；同一模型按大小写分裂成两行，速度与失败历史被切成两半。现在写入侧统一 `rawChannelId()` 剥标记、`entryKey()` 小写归一（界面显示名另存 `displayName`），启动时 `cleanupRuntimeSnapshotJunk()` 清历史脏行（清了几行会打一行 INFO）
- **决策留痕**：每次真实请求都现算一份候选排序快照。**内存环形恒存最近 200 条**（重启清空、不受采样影响），落库按 `rankTraceSampleRate`（默认 5%）抽样写 `data\llm-gateway.db` 的 `rank_trace` 表（单份快照 5~15KB，全量写会挤占 SQLite 单写连接反噬转发链路）；保留 `rankTraceKeepDays` 天且最多 3000 行，每条最多存前 40 行候选
- **口径**：综合分 = 13 个因子连乘（优先级 × 健康 × 质量 × 首字速度 × 出字速度 × 费用档 × 场景匹配 × 代码能力 × 人工权重 × 限流恢复 × 限流压力 × 工具弱 × 早停嫌疑），界面"因子"展开可逐项看；`实测中位首字/配置优先级/连续失败/质量问题/该家近5分钟撞墙/该家学到的额度(次/分)/长期429占比与样本数` 是诊断值，不参与连乘。服务端把每个因子按 4 位小数取整再回传，所以前端连乘与综合分只有末位之差
- **分摊对照的取数口径**（`/api/load-balance`）：实际侧＝窗口内 `usage_daily` **全部来源工具**之和（含网关内部压缩调用 `gw-compress`，它同样消耗真实额度；早期实现只统计 `client=''` 的行，把真实量少算了一半以上），可用 `?client=xxx` 只看某个工具；应得侧＝抽签席 `√(偏好分)` 权重的窗口均值，按 `rank_trace` **采样库 + 内存环形按 traceId 去重合并**，所以重启不会丢观测。零调用清单区分三种原因：路由里被停用 / 无启用渠道 / 已启用但零调用
- **端点**（带 `x-admin-token`）：`POST /api/rank-preview`（沙盘现算，只读）、`GET /api/rank-traces`（内存最近决策）、`GET /api/rank-trace/{traceId}`（含未落库时的明确说明）、`GET /api/load-balance?days=3[&client=]`（实际占比 vs 应得份额 + 未进席原因计数 + 零调用点名）、`GET|PUT /api/rank-trace-config`
- **门控出局顺序是契约**：无启用渠道 → 临时停用 → 档位不匹配 → 超上下文窗口。被门控剔除的候选根本不进打分，所以它们不出现在评分表里，而在"门控出局"区单列——这也是"某个模型为什么从没被调用"的第一种答案

## 7. 常见问题

**Q: `start.bat` 报 `[java missing]` / `[java too old]`？**
脚本按 `GW_JDK` → `tools\jdk-*` → `JAVA_HOME` → PATH 的顺序找 JDK，找到还会验版本 ≥21（低于 21 虚拟线程起不来）。报 `[java too old]` 时会把实测版本号和它在哪找到的都打出来——多数是 PATH 上有个老 JRE。解决办法：`set GW_JDK=<JDK 21 目录>`（指到含 `bin\java.exe` 的那一层，不是 `bin`）。

**Q: `start.bat` 报 `[layout error]`？**
`scripts\` 必须紧贴项目根（上一级要有 `pom.xml`）。把 `scripts` 单独拷走、或者只下载了仓库的一部分，就会报这个。

**Q: 启动提示 `[config missing]`？**
没建 `config\config.yaml`，按第 3 步第 2 步先复制模板。

**Q: 构建 `[BUILD FAILED]` 且提示 Unable to rename ... llmGateway.jar？**
网关还在运行占着 jar 文件。先跑 `scripts\stop.bat` 再重新 `scripts\build.bat`。

**Q: 构建时依赖拉不下来（公司内网 / 镜像不在网 / 离线）？**
`build.bat` 找 Maven 的顺序是 `GW_MVN` → `tools\apache-maven-*\bin\mvn.cmd` → PATH。镜像问题改你实际用的那个 Maven 的 `settings.xml`（或 `~\.m2\settings.xml`）里 `mirrors`，例如换成阿里云；有本地仓库目录也可以直接离线跑。作者开发机上另有一个不重跑 Maven、用自带 javac 热写进现有 jar 的 `jar-patch.bat`，它按本机布局写死，**未随仓库发布**。

**Q: 管理页打不开？**
`scripts\status.bat` 先看服务在不在；不在就看 `scripts\doctor.bat` 的 `port state`。端口被别的程序占了，就用 `set GW_PORT=<其它端口>` 重新启动（见第 3 节端口那条——改 `config.yaml` 的 `server.port` 是没用的）。

**Q: 工具报 401？**
API Key 与 `gateway-keys` 不一致。注意两者都不会自动去空格。

**Q: 查上游模型清单（或转发）报 `HTTP 403: {"error":{"message":"Forbidden"}}`，可同一个地址同一个 Key 在 Postman 里能通？**
Postman 跟随 Windows 系统代理，Java 的 HttpClient **不读**系统代理，所以网关是直连。若该供应商由 CDN 按出口 IP 在边缘拦截（groq 实测如此：本机直连被 Cloudflare 挡回 33 字节的 `Forbidden`，连无头浏览器同样被挡；走本地代理则能打到源站），直连必然 403，与 Key、路径、UA 都无关。
判据：错误体只有 `{"error":{"message":"Forbidden"}}` 且响应头带 `Server: cloudflare` / `CF-RAY`、无 `www-authenticate` → 边缘拦截；返回 `Invalid API Key` → 已经打到源站，那才是 Key 的问题。
处置：给该供应商填 `proxy: http://127.0.0.1:7897`（本地代理客户端的 HTTP 端口，Clash 常见 7890/7897），管理页"热重载配置文件"即可。注意代理出口节点本身也可能被拉黑（实测同一代理下有的节点 403、有的 200），换节点再试。

**Q: 模型清单里看不到我配置的模型？**
本网关默认**不拉取**上游模型列表（`defaults.catalogDiscovery: false`），清单只信你手工配置的 `static-models`。这是特性不是缺陷：避免上游几百个不可调用的模型混进来。想临时看看上游有什么，管理页"系统 → 自动发现"开关可开（看完建议关掉并删掉不用的）。

**Q: 请求慢？**
看管理页"请求日志"的 TTFT 列。慢的供应商会被速度学习自动降权；对冲竞速会在主选 2.5s 无响应时自动切换，无需人工干预。仍嫌慢可调小 `defaults.hedgeDelayMs`（如 1500）。

**Q: Agent 工具（DSH/Claude Code 等）聊得越久越慢、还总报"Prompt exceeds max length"？**
这是长会话固有问题：Agent 每轮携带全部历史，输入随轮次线性膨胀（实测可到 160K+ token），小窗口模型接不住、配额也烧得快。网关侧三招已内置：①给模型配 `contextWindow`（管理页模型编辑"上下文上限"）让超限模型自动出局；②开启上下文自动压缩（`contextCompressThresholdTokens` + `contextCompressModel`，见运行机制节）；③大请求对冲/评分污染已有防护。仍建议在 Agent 工具侧适当控制会话长度。

**Q: 开了上下文压缩，模型"忘了"很早之前说的事？**
压缩是有损的（极旧历史进摘要，最近 10 条保原文）。可把 `defaults.keepRecentMessages` 调大（如 20~30），或把 `contextCompressThresholdTokens` 阈值调高让压缩晚点触发。

**Q: 压缩功能怎么确认在工作？**
管理页"请求日志"里大请求的耗时骤降、免费渠道接住；或看响应头 `X-Gateway-Context-Compressed: true`；`logs/app.log` 里有"上下文压缩完成：约 XXX K → XX K token"字样。

**Q: 想让服务被局域网其它机器访问？**
临时：`set GW_HOST=0.0.0.0` 再 `scripts\start.bat`（脚本注入 `-Dserver.address`）。长期：改 `src\main\resources\application.yaml` 的 `server.address` 后重新 `build.bat`。注意 `config.yaml` 里的 `server.bind` 同样只是日志显示，不控制绑定。改完必须把 `gateway-keys` 换成强随机值，否则同网段任何人都能蹭你的 Key。

## 8. 安全注意

- `config\config.yaml` 含所有供应商 Key 明文，**不要**提交到 git/网盘/聊天工具；仓库的 `.gitignore` 已把它排除，但仍建议你在 `git add` 前确认一次
- `data\llm-gateway.db`（SQLite）与 `logs\` 含你的调用记录，同样不要外发（也已 `.gitignore`）
- 默认只绑 127.0.0.1，风险面最小；改成 `0.0.0.0` 之前先看上一条 Q
