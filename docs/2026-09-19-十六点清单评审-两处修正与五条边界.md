## 一、两处证据修正

### 修正 1：#3「并行多工具流式转换串台」——缺陷成立，机制描述不准

**原清单说法**：『OpenAI 流并行工具只有首个 chunk 带 id，后续增量全部拼进"最后打开的块"→ 第二个工具参数丢失』。

**修正后的机制**：第二个工具的**首 chunk 通常带自己的 id**，`AnthropicConverter.java:345-346` 的 `isNew` 判断会正常为它开新块——这条主路径没有问题。真正会丢参数/串台的是三种上游行为：

1. **续传 chunk 不带 id**（最常见）：某些 vLLM 系上游按 `index` 约定发增量，第二个工具从头到尾没有 id 字段 → `isNew` 恒为 false → 参数全部拼进第一个工具的单份 `toolArgs` 缓冲（`StreamState:237-238`）→ 第一个工具的参数被污染、第二个工具根本没有块；
2. **arguments 非 String**：流式 `:362` 的 `fn.get("arguments") instanceof String` 不匹配则**静默丢弃**（无 input_json_delta，tool_use 块 input 恒为 `{}`）；非流式 `:198` 强转 `(String)` 抛 ClassCastException 被 catch 吞成 `Json.obj()`。原文档对 ② 的判断正确，予以保留；
3. **交错或重复 id 的上游**：工具 B 的增量之间又插入带 id=A 的增量 → `isNew` 误判 → B 的块被提前关闭、A 重复开块。

**施工要求**：修法不变（按 `index` 维护 `Map<Integer, Block>`，`arguments` 兼容 String/Map），但**单测必须覆盖上述三种场景**，不能只测"两个并行工具的理想顺序流"。

### 修正 2：#5「persist 先写盘再校验」——不成立，剩余风险改述

**原清单说法**：『ConfigService.java:80-98 persist() 先写盘(:95) 再 reload 校验(:97)，坏配置已落地无回滚』。

**修正后的事实**：`ConfigService.persist()` 实际顺序是 **load 文件 → mutator 修改 → `validate(working)` → 写盘 → reload**——校验发生在写盘**之前**（:92 附近）。"坏配置无校验落盘"这条不成立。

**#5 剩余的真实风险**（仍是该修的理由）：

1. `ConfigWriter.java:157-160`：ATOMIC_MOVE 不支持时的回退路径是 `Files.deleteIfExists(target)` → `Files.move(tmp, target)`——进程死在这两步之间，target 已删、只剩 .tmp，**全部上游 Key 丢失**；
2. `q()`（:180-184）不做 YAML 引号/反斜杠转义，apiKey 含特殊字符时写出的 yaml 会坏。

**施工要求**：`.bak` 方案照做（target 先 rename .bak → move tmp → 成功后删 bak），但理由从"先写后验"改为"原子替换失败窗口"；persist 顺序无需改动。

## 二、五条执行边界（原清单未提，施工时必须带上）

### 边界 1（#13 空闲门控）：必须带"最大延迟"，否则熔断恢复会饿死

"在途请求 >0 则跳过/延后本轮探测"如果做成纯门控，**持续有流量的时段探测永远不跑**，半开熔断恢复验证（tryEnterHalfOpen 依赖探测触发）随之饿死。要求：在途 >0 延后本轮，但**延后累计超过 10 分钟强制执行一轮**。

### 边界 2（#10 压缩记账）：这是行为变化，不是纯观测

现状压缩 token 不进 usage_daily、不占日预算。补记账后：用量统计变真实（当前 84 次成功压缩零记账），**同时压缩开始占用日预算**——免费上游的可用额度会变少。这是诚实记账、方向正确，但要明确预期：上线后"日预算提前耗尽"如果是压缩引起，是记账归位而非新 bug。建议上线当天对照 usage 端点的 client 分桶确认量级。

### 边界 3（#11 流式占并发）：并发上限将真正生效，行为变严

`acquireInflight` 覆盖到 `streamToClient` 结束后，长流（最长 120s 心跳窗）期间会占住并发额度，concurrency limit 的条目会拒绝更多新请求。这是修复"形同虚设"的本意，但上线当天若某家"突然开始排并发/报 concFull"，是预期行为不是回归。

### 边界 4（#1 TTFT 修复）：修复当天速度样本会突变，提前记录免得误判

Anthropic 端 TTFT 从"整段流时长"变回"真首字"后，EWMA/中位数会**明显变快**（旧样本被系统性高估），分摊抽签与"极慢踢出"门槛的结论都会移动。**这是修复生效的表现，不是新 bug**。建议：修复上线时间记入运行日志；当天看到 Claude Code 流量对应模型的速度分跳变，直接对照本次记录，不要重新排查。

### 边界 5（#12 会话指纹）：只用首条 system 哈希不够

Claude Code 的子代理/多窗口/rewind 场景下，同一 client 的多个会话 system 完全相同，`system 哈希`做指纹分不开，滚动缓存照样互相覆盖。要求：指纹取 **「首条 system + 前 2 条 user 内容」的组合哈希**，并保留消息数单调性校验做兜底（消息数比上次还少且哈希不匹配 → 视为新会话，走全量压）。
