## 二、逐项核对详情

### 1a 压缩摘要定调指令 ✅

- 实现：`ContextCompressor.java:209-212`，定调指令注入在压缩摘要的 **system 消息**里，而非原方案的两个 prompt 常量。
- 评价：位置更优——全量压缩、增量压缩、硬截断兜底三条路径的产出都带上"任务仍在进行，该调用工具就发起工具调用，不要提前收尾"。硬截断的降级提示（`ContextCompressor.java:325-328`）同样写了"不要提前收尾"。

### 1b 保留最后一个完整 tool 组 ⚠️ 半实现

- 已做对的部分：`alignToToolGroupBoundary`（ContextCompressor 末段）保证压缩切点永不落在 tool 组中间——双向处理了"保留段开头是孤儿 tool"和"keepFrom 停在 owner 与结果串之间"两种情况，注释还修正了旧实现"只越过 tool 串导致上游 400"的坑。**常规场景**（保留最近 12~15 条）最后一个 tool 组确实原样保留。
- 未覆盖的边角：`computeKeepFrom` 从尾部按 token 预算（keepRecentTokens=16000）往前累加。若**最后一条消息恰好是一个超预算的大工具输出**（agent 场景常见：刚跑完命令吐几万字，正等模型续），预算循环在 owner 之前截断，此时边界对齐的 case 1 选择"把整组**向后推给摘要**"而不是"把 owner **拉进保留段**"——整个最后的 tool 组被吞进摘要，保留段甚至可以为空。这恰好是 1b 要治的"刚刚发生了什么被吞掉"场景。
- 建议修法：case 1 从"向后吞结果串"改为与 case 2 同方向的"向前拉 owner"（把 keepFrom-- 到 owner 处），让两个方向一致地"保留整组"；超大输出交给已有的 `shrinkOversizedText`（头 70% + 尾 30% 截断）消化。

### 1c 弱工具模型评分降权 ⚠️ 未通电

- 机制已完整：
  - TW 因子 ×0.35，软降权不剔除（`PolicyService.java:500-504`），"rank 永不返回空"铁律保住；
  - **超出原方案**：新增 ES 早停嫌疑因子——client×provider×model 维度，"压缩后无工具调用且回复 <24 字符"记 10 分钟惩罚再叠 ×0.5（`PolicyService.java:722-746`），后续真实发起工具调用自动解除。三条件缺一不可，不压缩的正常短答不会误伤。
  - hasTools 由两端点正确传入（GatewayController:134-135、AnthropicController:169-170，用 `RequestCategoryAnalyzer.requiresTools(req)`）。
- **问题：config.yaml 的 routing-overrides 里没有任何模型标 `toolWeak: true`**——TW 恒为 1.0，机制空转。管理页/API 已支持打标（AdminController:128/262/274、ConfigWriter:122）。
- 交付前动作：在管理页把 glm-4-flash 等已知工具弱的模型标上 toolWeak。

### 2a responseHeaderTimeoutMs=5s ⚠️ 有严重副作用（本次验收最重要发现）

- 已做对的部分：`HttpRequest.Builder.timeout(headerMs)` 真接到 HTTP 层（`ForwardEngine.java:174-191`），不再是死配置；超时抛 `HttpTimeoutException` 被捕获并标记可重试失败，调用方可立即换渠道。
- **严重副作用**：headerMs 对**流式和非流式一律 5 秒**。对流式没问题（SSE 头即时发）；对非流式，多数上游"算完整个响应才发响应头"，5s 实际变成**总响应时限**。
- **live 实锤**：新网关 23:23 探测日志中，glm-4.5-flash、glm-4.7-flash 等平时秒回的正常模型，8-token 的 ping 都被"响应头超时(>5000ms)"判死；重启前（00:09–06:38）同一模型全天 OK。探测是非流式小请求，直接证明非流式语义被破坏。
- **连锁影响**：压缩 = 非流式 + 165K 输入（9-13 日实测 165K→6K 正常工作），5 秒内响应头不可能到达 → 压缩候选链全会超时 → 静默退到硬截断兜底。**压缩功能（连同 1a/1b 的成果）对大上下文名存实亡。**
- 建议修法（一行）：headerMs 仅对 `stream=true` 生效，非流式用 budgetMs。

### 2b reasoning_content 算真实首字/活动性 ✅

- 边界严格按约定实现：
  - `openAiDataHasContent`（`ProtocolAdaptor.java:59-78`）：content / **reasoning_content** / reasoning / tool_calls 均算"真内容"，喂 TTFT 闸门与心跳续命；注释明确引用"19 条首字超时实锤"。
  - OpenAI 适配器 isRealFirstToken 委托该函数 → 思考流算真首字，推理模型不再被 TTFT 闸门误换家。
  - **结论判定没有放开**：流式空回复判定只认 content+tool_calls（GatewayController:593），非流式同样（GatewayController:543）——"狂思考但空正文"仍按软失败降权，正是约定的"活动性/结论"边界。
  - 心跳窗口改为出 token 后统一宽窗 120s（配置 firstTokenHeartbeatTimeoutMs），长思考模型不再被 30s 窗误杀。
- 已知缺口（零实害）：Anthropic 出站适配器 isRealFirstToken 只认 text_delta/input_json_delta，thinking_delta 不算。当前 7 家上游全为 openai 协议，暂无影响；将来接 anthropic 协议思考模型时需补。

### 2c CLIENT_ABORTED 落库 ✅

- 流式：写客户端 IOException → 状态 CLIENT_ABORTED（GatewayController:435-441、AnthropicController:394）。
- 非流式：上游成功但写客户端失败 → 状态从 OK 改记 CLIENT_ABORTED，备注 "client disconnected before delivery"（GatewayController:202-211、491）。
- "日志全绿但工具没收到"的可观测性黑洞补上；不动转发逻辑，纯加观测，符合方案。

### 3a 探测隔离 ✅（留一个钱尾巴）

- 隔离彻底（`PolicyService.java` recordSuccess/recordFailure 探测分支）：
  - 成功：不进 EWMA/中位数/吞吐窗、不清真实失败计数、不记预算（addUsage 前提前 return）、不进限流学习窗口；仅保留半开熔断恢复验证。
  - 失败：只留 lastError，不推动主熔断状态机；但 429 的 Key 级冷却保留（上游真实配额信号，合理）。
- live 验证：23:22 amd/DeepSeek-V4-Flash 探测两连败（两把 Key），未触发主熔断。
- **尾巴**：探测每 30 分钟扫全部 free 模型，openrouter/free ≈ 48 次/天，对着它真实的 50 次/天上限。3a 只隔离了网关自己的预算账，**探测烧上游真额度的问题没有解决**（这正是 3a 立项动机之一）。建议：把 openrouter/free 排除出探测，或对配额硬顶供应商单独降频。

### 3b 4xx 不计熔断、401/403 只冷却 Key ✅

- 401/403：只冷却对应 channelId（quotaCooldownMs 时长），不推熔断计数（`PolicyService.java:793-801`）——错误本就带 channelId，"Key 能否定位"的疑问不存在。
- 其余 4xx（400/404/422 等）：只留 lastError，不熔断（:802-809），注释记录了"152K 大请求 400 三次打熔断好模型"的实测教训。
- 429 维持原有冷却快通道 + 配额耗尽长冷却 + Retry-After 精确冷却。

### 3c 半开恢复单条放行 ✅

- 比原方案完整：冷却到期后 `tryEnterHalfOpen` 置位（两控制器 + ProbeScheduler 三处触发），rank 里 `tryClaimHalfOpen` CAS 抢槽——同一时刻仅一条在途请求验证恢复，其余并发继续按冷却处理。
- 还带了 **60 秒持有超时自动放槽**（`PolicyService.java:863-873`）——防探路请求自身挂死把半开悬置（正是评审时提醒的点）；成功关闸、失败放槽并计数，状态闭环。

### 3d 日预算双计数修复 ✅

- `tokensUsedProvider` 求和时跳过 `\u0001` 标记的 channel 行（`PolicyService.java:575-585`）；`channelKey = providerId + "\n\u0001" + channelId`，分隔符与过滤严格匹配；entry/channel/Key 三级预算各自读取各自键，不再混装双计。
