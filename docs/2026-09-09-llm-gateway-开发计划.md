# 大模型 API 网关（LLM Gateway）开发计划

> 日期：2026-09-09 ｜ 状态：待确认 ｜ 作者：ZCode 草拟

> 配套文档：[概要设计](./2026-09-09-llm-gateway-概要设计.md)

## 一、需求理解

你要做一个**本地大模型 API 网关**：

1. **渠道管理**：统一管理你手上多家大模型服务商（OpenAI、Anthropic、DeepSeek、月之暗面、智谱等）的 API Key，每个渠道可配置费率、限速（RPM/TPM）、优先级。
2. **智能转发**：程序监听一个本地端口，AI Agent 工具（Claude Code、Cline、自研 Agent 等）把 `base_url` 指向它即可，路由由网关决定。
3. **路由策略**：默认"哪个快用哪个"（按实测延迟选路）；优先级手工可设且分**两个维度**——不同提供商之间设基础优先级，同一提供商内不同模型还可单独覆盖；同时在**速度与省 token（保住额度）之间做平衡**，不能把免费/赠送额度一下烧光。
4. **无感容错**：失败自动切换备用渠道，任何环节都有超时兜底，对 Agent 完全无感。

## 二、架构设计

```
AI Agent 工具
    │  OpenAI 兼容协议 (base_url=http://127.0.0.1:8317/v1)
    ▼
┌─────────────────────── LLM Gateway ───────────────────────┐
│ ①接入层  统一 /v1/chat/completions /v1/models + 本地鉴权  │
│ ②路由层  模型名→候选渠道列表 → 策略打分 → 选一个           │
│ ③策略层  优先级 × 健康度 × 速度(EWMA) × 限速余量           │
│ ④适配层  协议转换器：OpenAI ⇄ Anthropic / Gemini / 其他    │
│ ⑤转发层  SSE 流式透传、首token前失败自动重试下一渠道        │
│ ⑥统计层  TTFT、成功率、tokens 用量、费用 → SQLite          │
│ ⑦管理层  REST API + 简单 Web 页面（状态/开关/调优先级）    │
└───────────────────────────────────────────────────────────┘
    ▼ 按渠道适配后的原生请求
OpenAI / Anthropic / DeepSeek / 智谱 / 月之暗面 / 本地 Ollama ...
```

### 核心数据模型（三层 + 模型目录）

- **提供商（Provider）**：一家服务，一个 base_url + 鉴权方式 + 协议类型。
- **渠道（Channel）**：提供商下的**一个具体 Key**。同一提供商多个 Key 构成渠道池，轮转分摊限速。
- **模型目录（Model Catalog）**：**不手工枚举模型映射**。网关后台定时调用各家 `/v1/models` 自动发现该提供商支持的全部模型，聚合成统一目录；某家不支持此接口的，允许在配置里补一个静态模型清单。请求进来后按 `model` 名匹配，**所有支持该模型的渠道自动进入候选池**：
  - 直接名称匹配：`deepseek-chat` → 官方、硅基流动等所有提供此模型的渠道都是候选；
  - 前缀指定：`siliconflow/deepseek-chat` 强制走某家（同名模型多家都有、想点名时用）。
- **优先级（双维度）**：提供商设**基础优先级**；同一提供商内**每个模型可单独覆盖优先级**（如智谱整体优先级 1，但免费的 glm-4-flash 提到 0 常用，贵的 glm-4-plus 降到 5 省额度）。路由条目粒度是 (提供商, 模型)，有效优先级 = 模型覆盖值（未设置则用提供商基础值）。
- **模型分组（虚拟模型）**：可自定义虚拟模型名（如 `fast-cheap`），组内成员是多个 (提供商, 真实模型) 条目、各带优先级——Agent 请求虚拟名，网关在组内按优先级+策略选路。适合把"同一档能力"的多家模型组成一个池，也用于各家模型名不一致时的归一。

### 路由策略（"哪个快用哪个"的落地）

不能拿单次延迟做决定（抖动大，会在两个渠道间来回震荡），用**综合评分**：

```
 Score = 优先级权重 × 健康系数 × 速度系数
 速度系数基于 TTFT（首 token 延迟）的 EWMA 指数平滑值
 健康系数：连续失败/429 → 熔断冷却（指数退避），冷却期内分数趋零
```

策略模式可切换：`priority`（严格按优先级）/ `latency`（速度优先）/ `weighted`（加权随机）/ `auto`（综合，默认）/ `cost-first`（费用优先）。

### 速度与省 token 的平衡（额度治理）

"哪个快用哪个"和"省额度"天然有张力——最快的往往也是额度消耗最狠的，必须有治理机制防止"一下把额度烧光"：

1. **费用感知选路（cost-aware）**：渠道条目可标注费用档位（free / low / standard / premium）。`auto` 策略默认**优先用免费/低价档**，只有当低费档全部不可用（限流/熔断/超时预算耗尽）时才逐级升到高价档——"贵的留着兜底，便宜的先用"。
2. **Token 配额与日预算**：每个 (提供商, 模型) 条目（或提供商整包）可设：
   - `daily_token_limit`：每日 token 上限，用完该条目当日自动摘除（次日零点重置）；
   - `concurrency_limit`：并发上限，防瞬时洪峰烧额度（各家限速 RPM/TPM 也同时生效）。
   网关本地累计 tokens 用量（从响应的 usage 字段统计），到达阈值自动降级到下一优先级。
3. **关键豁免**：支持给 Agent 侧请求打标（如请求头 `X-Gateway-Profile: critical`）豁免费用治理——重要任务走高速通道，不被省钱策略卡住。
4. **预警与可视化**：额度使用率 70%/90% 阈值告警（管理页醒目提示，可选本地通知）；费用报表按渠道/模型/天聚合，让"钱花哪儿了"一眼可见。

> 设计原则：**速度策略负责"当下这次请求走谁最快"，额度治理负责"这个月的量够不够烧"**——两层解耦，互不干扰，各司其职。

### 关键机制

- **SSE 流式透传**：Agent 几乎全用流式，这是硬需求。规则：**首 token 之前**失败可换渠道重试（上限 2~3 次防雪崩）；已开始输出则不切换。
- **429 处理**：识别限流响应，识别 `Retry-After`，该渠道进冷却，立刻换下一个。
- **熔断**：连续 N 次失败（默认 3）→ 冷却 60s 起步，指数退避，最长 30 分钟，期间半开探测。
- **多 Key 轮询**：同提供商 Key 池轮转/加权轮转，撞限流的 Key 暂时摘除。
- **本地鉴权**：网关自己发 1~N 个本地 Key，防局域网蹭用；Key 落盘加密（不写明文进 git）。

### 响应速度保障机制（为什么请求永远不会"半天不响应"）

这是本项目的**存在意义**，核心思路是一句话：**链路上每个环节都有超时和逃生通道，任何环节都不能"无限等"**。具体分三层兜底：

1. **TCP 层硬超时**：连接建立 3 秒、响应头到达 5 秒，到点即掐——不会把时间浪费在已经死掉的渠道上。
2. **渠道预算（channel budget）**：每个候选渠道有总时间预算（默认 30 秒，TTFT 小于 10 秒），预算耗尽立刻切下一家；所有候选耗尽前透传上游自己的 5xx/慢响应给 Agent，让 Agent 自己决定。
&emsp;※ 就算真的进了流式阶段，中途彻底卡死的情况——中间没有 SSE 事件的心跳超时（默认 30s）也会掐掉，不留死角。
3. **全链路并行加速**：入站请求多路复用（虚拟线程 + 连接池复用 TCP/TLS）；模型目录预拉取并缓存（后台每 5 分钟刷新 `/v1/models`，请求路径上零远程调用）；`/v1/models` 聫动响应、管理页数据全部走本地缓存，永远不需要等远程。

配合路由层的 EWMA 延迟统计，正常情况下请求会自然流向 TTFT 最低的渠道；而某个渠道抽风时，最多一个预算周期（默认 30s）内流量就会自动迁走——**这是"哪个快用哪个"的全部含义：好渠道自然被选中，坏渠道自然被淘汰，不需要人工干预**。

> 量化验收标准（阶段 2 结束时）：
> - 主渠道网络断开 → Agent 的请求**秒切**备用（体感 < 1s，即 TCP 失败立即换，不消耗预算）。
> - 主渠道挂羊头卖狗肉式变慢（连接成功但响应极慢）→ 该渠道的预算内流走，< 30s 切走。
> - 8 家提供商 × 平均 40 个模型 ≈ 320 个模型规模下，网关自身开销（不含上游返回时间）< 50ms。

## 三、技术选型（推荐方案 A）

| 方案 | 栈 | 优劣 |
|---|---|---|
| **A. Java 自研（推荐）** | Java 21 + Spring Boot 3 + 虚拟线程 + Java HttpClient 流式 + SQLite | 你最熟，长期好维护；虚拟线程下 SSE 透传很轻；个人工具量级绰绰有余 |
| B. 直接用开源 | LiteLLM Proxy（Python）/ One API、New API（Go） | 零开发、功能全；但"哪个快用哪个"等自定义策略不好做，多一套运行时依赖 |
| C. Go 自研 | Go + 标准库反代 | 部署单文件最优雅，但你不写 Go，维护成本高 |

> 建议：先花半小时装一遍 LiteLLM/One API 体验，再决定自研范围——自研的价值恰恰在**动态选路策略**这类现成品做不好的点上。若确认自研，按方案 A。

**环境准备**：本机默认 JDK 1.8 + Maven 3.5.3，需安装 JDK 21（如 Temurin）+ Maven 3.9，均可与现有项目并存。

## 四、开发计划（分五期，总计约 8~11 个业余时间日）

### 阶段 0：骨架打通（0.5 天）
Spring Boot 工程；`/v1/chat/completions` 纯透传到单个 OpenAI 兼容上游；验证 SSE 流式不缓冲、不断流。**验收：curl 流式返回正常。**

### 阶段 1：MVP——能用（2~3 天）
- 配置模型落地（YAML）：provider / channel 配置，模型映射由目录自动发现
- 本地 Key 鉴权
- 双维度优先级（提供商基础 + 模型覆盖）路由 + 失败自动 failover（重试下一渠道）
- TCP/响应头双超时 + 渠道预算机制（响应速度保障的第一层、第二层兜底）
- Anthropic 协议适配器（OpenAI 格式 ⇄ Claude 原生格式，含流式转换）
- **验收：Claude Code / Cline 把 base_url 指向网关即可干活；主渠道断网/失效 Key 时自动切备渠道，Agent 无感。**

### 阶段 2：策略——好用（2~3 天）
- 模型目录后台定时刷新（默认 5 分钟）+ 前缀点名路由（`siliconflow/deepseek-chat`）+ 模型分组（虚拟模型）
- TTFT 采集 + EWMA 平滑、成功率统计
- EWMA + 熔断 + 429/Retry-After 冷却
- 策略模式切换（priority / latency / weighted / auto / cost-first）
- 同提供商多 Key 轮询与限流摘除
- 流中心跳超时（响应速度保障的第三层兜底）
- **验收：人为制造某渠道变慢/429，网关 10 秒内自动把流量迁走；恢复后自动回切。**

### 阶段 2.5：额度治理——不烧光（1~2 天）
- Token 用量本地累计（解析响应 usage 字段，流式末尾的 usage 也要接住）
- (提供商, 模型) / 提供商整包 两种粒度的 `daily_token_limit` + `concurrency_limit`，超限自动降级/摘除、次日重置
- `auto` 策略费用感知选路（free → low → standard → premium 逐级兜底）
- 关键请求豁免标记（`X-Gateway-Profile: critical`）
- **验收：把某免费条目日限设为极小值，跑几轮请求后网关自动改走付费备用；次日额度重置；`critical` 请求始终走高费高速通道。**

### 阶段 3：可视化与持久化——省心（2~3 天）
- SQLite 持久化：请求日志、按天/渠道/模型聚合 tokens 与费用
- 管理 REST API + 单页 Web：实时渠道健康、延迟曲线、**额度使用率与 70%/90% 预警**、手动禁用/置顶、改优先级热生效
- **验收：打开 `http://127.0.0.1:8317/ui` 一眼看到所有渠道状态、额度水位，并可直接操作。**

### 阶段 4（可选增强）
配置热加载；更多适配器（Gemini、embedding、Responses API）；会话亲和（同一会话尽量钉住渠道利用各家前缀缓存提速）；额度/费用日预算告警；对外暴露 `/v1/models` 聚合各家模型清单。

## 五、风险与注意点

1. **协议适配是最容易踩坑的部分**：Claude 的 messages/system/tools 与 OpenAI 格式差异大，流式事件结构完全不同；建议第一阶段只做一个非兼容协议（Anthropic），其余供应商大多 OpenAI 兼容，直接透传。
2. **不要吞掉 `max_tokens`/`stream_options` 等参数语义**，透传时逐字段核对。
3. **Key 安全**：配置文件不进 git（`.gitignore` + 加密存储），日志里脱敏打印 Key。
4. **延迟测量公平性**：不同模型速度天然不同，TTFT 统计按"模型 × 渠道"维度分开，不能跨模型比较。
