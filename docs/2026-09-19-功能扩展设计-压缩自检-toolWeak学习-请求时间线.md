# 功能扩展设计：压缩链路自检 / toolWeak 自动学习 / 请求时间线

- **日期**：2026-09-19
- **状态**：方案设计（待评审，未实现）
- **来源**：三组十项改造验收（2026-09-18）与整夜运行后梳理出的三个功能缺口
- **原则**：每项都刻意做成小改动，不碰转发主流程；告警永远不影响请求成功（与压缩"铁律"同哲学）

## 0. 总览

| # | 功能 | 动机一句话 | 优先级 | 预估工作量 |
| --- | --- | --- | --- | --- |
| 一 | 压缩链路一键自检 | 2a 事故证明：压缩被打残后一切照常成功，没有任何卡片会显示 | 高 | 1~1.5 天 |
| 二 | toolWeak 自动学习 | 1c 机制完整但靠人肉打标，且模型会变，名单永远追不上现实 | 高 | 1 天 |
| 三 | 请求时间线（trace） | request_log 没有 trace_id，同一次失败的多行拼不起来，诊断靠时间窗人肉对齐 | 中高 | 1 天 |

三项相互独立，无实现依赖，可任意单独做。建议顺序：三（改动最机械、立刻提升排障效率）→ 一（能当场验证一批配置类回归）→ 二（需要积累样本，越早上线越早见效）。

## 一、压缩链路一键自检

### 1.1 背景与依据

- 实锤事故（2026-09-18 验收报告）：2a 的 5s 响应头超时误伤非流式请求，压缩候选链全会超时 → 静默退到 hard-truncate 兜底。**请求全部成功、日志全绿，压缩功能名存实亡，只有翻日志才能发现。**
- 压缩是本网关的核心增值能力（1a/1b 的大额上下文治理），却没有一条"它现在好不好使"的客观验证路径。

### 1.2 目标 / 非目标

**目标**：管理页一个按钮，串行跑三类检查并出一张体检报告卡片，当场暴露"配置改坏了某条链路"这类回归。

**非目标**：不做定时自动体检（手动触发即可，将来需要再加）；不做体检结果自动改配置（只报告，人确认）。

### 1.3 交互设计

管理页新增"一键体检"按钮 → 异步启动 → 卡片实时显示进度与结果。三类检查：

1. **上游探测**：复用现有探测轮（ProbeScheduler 逻辑），不重复造轮子；
2. **压缩链路干跑**：构造一份固定的 ~5K 字符模拟对话（含 user/assistant/tool 消息），走一遍压缩候选链（`ContextCompressor.callCompressor` 路径），报告：走的是 full/incremental 哪条路径、命中的候选、耗时、产出摘要字数；候选链全失败 → 红色告警"压缩链路不可用，当前大上下文会退到硬截断"；
3. **工具调用测试**：每个 free 档模型发一条极小请求（带一个 trivial 工具定义如 `get_weather`，max_tokens=32），判定响应里有没有 `tool_calls` → 每模型给出"工具调用 ✓/✗"结论。

### 1.4 技术设计

- 新增 `SelfCheckService` + `POST /admin/selfcheck/run`（异步，虚拟线程执行）+ `GET /admin/selfcheck/status`（轮询进度/结果）。
- **隔离（关键）**：体检请求带 `client=selfcheck`，复用探测隔离机制——现在 PolicyService 里隔离判定是 `"probe".equals(client)`，扩展为一个集合 `{probe, selfcheck}`：体检请求不进 EWMA/中位数/吞吐、不进预算、不进限流学习、失败不进主熔断。**不扩这个集合的话，每次体检会污染速度样本**（5K 输入的压缩 TTFT 代表不了 100K 真实请求）。
- 压缩干跑复用 `callCompressor`，但**绕开滚动缓存**（不传真实 client，不读写 rolling map），避免把体检样本写进真实会话的滚动状态。
- 结果落 request_log（client=selfcheck），方便回溯历史体检记录。

### 1.5 防呆与边界

- 全程串行执行（同探测轮），避免体检自己把免费上游打出限流；
- 工具测试的 ✗ 结论**只展示、只作为 toolWeak 学习的参考样本**（见第二节），不自动改任何路由配置；
- 体检中网关照常服务，互不影响（隔离保证）；
- 压缩干跑样本固定 → 结果可复现、可对比（这次 5s 超时、上次 8s 成功，一目了然）。

### 1.6 影响面

- 新文件 1 个（SelfCheckService）、Admin 端点 2 个、PolicyService 隔离判定从单值改集合（2 处调用点）、前端一个按钮+卡片；
- 不碰 ForwardEngine/压缩主路径/熔断状态机的任何现有逻辑。

### 1.7 验收标准

- 点按钮 2 分钟内出完整报告；期间正常聊天请求不受影响；
- 故意把 contextCompressModel 配成不存在的组 → 报告红色告警（模拟 2a 类事故能当场发现）；
- 体检前后 EWMA/预算/熔断计数零变化。

## 二、toolWeak 自动学习（半自动：建议 + 人审）

### 2.1 背景与依据

- 1c 的 TW 因子（×0.35）机制完整（PolicyService:500-504），管理页/API 也支持打标，但 config.yaml 至今没有任何模型标 `toolWeak: true`——因子空转；
- 手动打标的根本问题：弱模型是**发现出来的**（某个 agent 在它上面反复拿不到 tool_calls 才知道），人肉发现永远滞后，新接的模型又得重新踩。

### 2.2 目标 / 非目标

**目标**：网关自动统计每个 (provider, model) 的"带 tools 请求"样本，满足条件的在管理页弹建议、你一键确认生效。名单自动跟上现实。

**非目标**：不自动生效（永远人审，防止误标把好模型排后）；不基于单次失败判定。

### 2.3 判定规则

新增按模型累计的两个计数器：

- `toolsRequestsSeen`：带 tools 定义的请求数（复用 `judgeEarlyStop` 已有的 `requiresTools(req)` 判定入口，它在两个端点都已被调用）；
- `toolCallsEverSeen`：该模型历史上是否**从未**回过 tool_calls。

**建议条件**：`toolsRequestsSeen ≥ 20 && toolCallsEverSeen == 0` → 管理页"模型巡检/路由"区显示"建议标记 toolWeak"徽标（附带样本数），一键确认走现有 AdminController 的 toolWeak 写入路径（已有，写回 yaml）。

**反证机制**：已标记的模型一旦真实回过 tool_calls → 记一条"矛盾"计数展示在管理页（不自动摘标——可能是上游升级或换了模型，由你判断）。

**样本来源补充**：自检（第一节）的工具调用测试结果**计入**这两个计数器——弱模型连 trivial 工具都调不出来正是强证据；但单条样本永远不够触发阈值，只起加速作用。

### 2.4 技术设计

- 计数器内存维护（ConcurrentHashMap，与 earlyStopPenalty 同风格），**重启清零可接受**（攒样快，一两天就有结论）；如需跨重启，可在 `runtime_snapshot` 表加两列（该表已有 ON CONFLICT UPDATE 的快照机制，加列成本低）——做成可选增强，第一期内存即可。
- 新增 `GET /admin/tool-weak-suggestions`：返回满足建议条件的模型清单 + 样本数；
- AdminController 路由编辑处加"建议"徽标展示与一键应用。

### 2.5 防呆与边界

- 只统计真实流量的带 tools 请求；probe/selfcheck 的普通探测（不带 tools）天然不进样本；
- 压缩调用（无 tools）不进样本——`judgeEarlyStop` 现有判定已保证；
- 阈值 20 次可配置（defaults.toolWeakSampleThreshold，默认 20）；
- 已标记 toolWeak 的模型不再重复建议。

### 2.6 影响面

- PolicyService 加两个计数器字段 + judgeEarlyStop 里两行累计；Admin 端点 1 个；前端徽标；
- 评分公式 TW 因子本身零改动——本功能只解决"名单从哪来"。

### 2.7 验收标准

- 在一个已知弱模型上模拟 20 次无 tool_calls 的带 tools 请求 → 管理页出现建议徽标；
- 一键应用后 config.yaml 出现 `toolWeak: true`，后续带 tools 请求中该模型排序实际后移（可用 rank 日志验证）；
- 正常模型（回过 tool_calls）永不触发建议。

## 三、请求时间线（trace_id 串联）

### 3.1 背景与依据

- request_log 每次 attempt 各记一行（FAILED/OK/CLIENT_ABORTED/STREAM_TIMEOUT 等），**但没有 trace_id**——同一次客户端请求的"候选 A 失败→候选 B 失败→候选 C 成功"三行拼不起来；
- 实际排障（9-18 验收）靠 client+model+时间窗人肉对齐，是"排查标准流程"里最耗时的一步；
- 对冲竞速（HedgedExecutor）让一次请求可能产生并发 attempt 行，没有 trace 完全无法还原。

### 3.2 目标 / 非目标

**目标**：任何一行请求日志一键展开成完整时间线：候选顺序、每次 attempt 的状态/耗时/失败原因、压缩路径、最终交付状态。

**非目标**：不做分布式链路追踪（无 spans/采样/存储全家桶，一列 + 一个查询端点够用）；不改日志保留策略（随 request_log 现有 30 天清理同生共死）。

### 3.3 技术设计

- **schema**：`ALTER TABLE request_log ADD COLUMN trace_id TEXT`（旧行为 NULL，UI 显示"无链路"）+ `CREATE INDEX idx_request_log_trace ON request_log(trace_id)`。SQLite 加列与建索引在此数据量级都是秒级。
- **生成**：三个入口（GatewayController 聊天、AnthropicController、images 端点）收到请求时生成 `traceId`（如 `"t" + epochMillis + "-" + 4位随机`），同一请求内所有 logRequest 调用携带；
- **透出**：响应头加 `X-Gateway-Trace-Id`——工具端/用户侧日志里记下它，出问题拿着 ID 直接来管理页查，双向可对；
- **写入**：`StatsService.logRequest` 与 `StatsDao.insertRequestLog` 签名各加一个参数（约 15 个调用点，机械改动；也可重载一个带 traceId 的新方法、旧签名生成无 trace 行，改动更小）；
- **查询**：`GET /admin/trace/{traceId}` → 按 ts 排序的全部行 + 前端日志页每行一个"链路"按钮展开侧栏：垂直时间线，每 attempt 一行（状态徽标 + 耗时 + 截断的错误信息 + 压缩路径），最终交付状态高亮；对冲竞速的两条并发行并排标注"对冲"。

### 3.4 防呆与边界

- traceId 生成失败/为空 → 照常落库（trace_id NULL），绝不因观测失败影响请求（与 CLIENT_ABORTED 同哲学）；
- index 只建在 trace_id 上，不膨胀常用查询路径；30 天清理 SQL 不需要改（整行删除）。

### 3.5 影响面

- 一列 + 一索引 + 一个查询端点 + 前端展开交互；StatsService/StatsDao 签名动一处（或加重载）；
- 转发、评分、熔断逻辑零改动——这是三项里行为风险最低、排障收益最直接的一个。

### 3.6 验收标准

- 构造一次"候选 A 超时→候选 B 成功"的请求 → 日志两行共享同一 trace_id，点开看到完整两段链路；
- 客户端响应头能拿到 X-Gateway-Trace-Id 且与管理页一致；
- 旧日志行（无 trace_id）正常展示不报错。

## 四、共同原则与风险

- **三项都不碰转发主流程**：自检走隔离、学习只读现有判定入口、trace 只加观测列——任意一项出问题，最坏结果是"功能本身不工作"，不会波及请求成功率；
- **回滚**：三项各自独立开关（自检不点就不跑；学习只出建议不改配置；trace 列可空），逐项灰度上线，出问题单关即可；
- **依赖**：均无新第三方依赖（自检复用探测与 HttpClient；学习复用 judgeEarlyStop；trace 复用 SQLite）；
- 与告警方案（另文档讨论）的关系：自检的红色结论与 toolWeak 建议将来可挂到告警 webhook 上，第一期不做。
