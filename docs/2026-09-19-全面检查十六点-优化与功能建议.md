## 一、真 bug：发现即该修（第一优先）

### 1. Anthropic 端把"整段流时长"当成 TTFT —— 一行修复
- **证据**：`...\src\main\java\com\gw\gateway\AnthropicController.java:333` 对每条真内容行无条件执行 `firstTokenAt = String.valueOf(now - startMs)`；对照正确写法 `...\src\main\java\com\gw\gateway\GatewayController.java:346` 的 `if (firstTokenAt == null)`。
- **影响**：Claude Code 全部 `/v1/messages` 流量的 TTFT 样本实际=流总时长 → 灌进 EWMA、中位数环窗、速带分摊"极慢踢出"门槛，且与 OpenAI 端流量混在同一个 (provider,model) 键 → 免费上游被系统性误判为慢、好候选被误踢。
- **修法**：加 `if (firstTokenAt == null)` 守卫。收益极高 / 风险零 / **约 5 分钟**。

### 2. 上游 EOF 补收尾硬编码 `stop_reason:"end_turn"` —— 工具流被判"答完了"
- **证据**：`...\gateway\AnthropicController.java:379` 补收尾恒发 `end_turn`；同文件 `:353` 已收集 `streamSawToolUse` 却没参与收尾判断（只进了 `:388` 的事后记账）。
- **影响**：不带 `[DONE]`/finish_reason 的兼容上游 + 流内有 tool_use 时，Claude Code 收到 `end_turn` 即认为无需执行工具 → **静默早停的另一真凶**（本项目头号命题）。
- **修法**：`StreamState` 记 `sawToolUse`，收尾改发 `stop_reason:"tool_use"` 并补齐 `input_json_delta` 闭合。**约 0.5 小时**。

### 3. 并行多工具流式转换：单槽状态在三种上游行为下串台/丢参数（机制已按评审改述）
- **证据**：`...\provider\adaptor\AnthropicConverter.java:237-238` 只有一份 `currentToolId/toolArgs` 状态；`:345-346` `isNew = id!=null && 非同id`——**并行工具首 chunk 带自己 id 时主路径正常开新块（此点评审修正成立）**，真正丢参数/串台的是三种场景：
  1. **续传 chunk 不带 id**（vLLM 系按 `index` 约定发增量）：`isNew` 恒 false → 第二个工具的参数全部拼进第一个工具的单份缓冲，且第二个工具根本没有块；
  2. **arguments 非 String**：流式 `:362` `instanceof String` 不匹配则**静默丢弃**（tool_use 块 input 恒 `{}`）；非流式 `:198` 强转抛 ClassCastException 被 catch 吞成 `Json.obj()`；
  3. **交错/重复 id**：B 的增量间又出现 id=A → B 块被提前关闭、A 重复开块。
- **影响**：模型发 2 个工具、网关只交付 1 个可用的。**"准"的最大单点损失**，也是早停上游成因之一。
- **修法**：按 `index` 维护 `Map<Integer,Block>`；`arguments` 兼容 String/Map。单测**必须覆盖上述三种场景**（不能只测理想顺序流），沿用项目 main 直跑惯例。**约 0.5 天**。

### 4. images/raw 转发路径无视总预算，且读失败被记成功
- **证据**：`...\forward\ForwardEngine.java:299-346(executeImages)`、`:352-398(executeRaw)` 接收 `deadlineNanos` 但方法体内从不使用；`:337/:389` 无预算阻塞 `readAll`；`:410-416` `readAll` catch IOException 后 **返回空串** → 上层把 `"{}"` 当正常响应回写并记 SUCCESS。
- **影响**：中途断流 → 客户端拿到空 `{}` 无结论即自行终止；非流式聊天路径（`:256-266` 虚拟线程 Future+剩余预算）已解决，这两条没跟上。
- **修法**：抽带 deadline 的读工具复用；失败抛/返回 null 并记 FAILED。**约 2 小时**。

### 5. 写配置回退路径"先删后改名"，存在丢全部上游 key 的原子性窗口
- **证据**：`...\config\ConfigWriter.java:157-160` ATOMIC_MOVE 不支持时回退为 `Files.deleteIfExists(target)` → `Files.move(tmp,target)`——进程死在这两步之间则 target 已没、只剩 .tmp，**全部上游 Key 丢失**；`q()`(`:180-184`) 不做 YAML 引号/反斜杠转义，apiKey 含特殊字符会写坏 yaml。

- **修法**：target 先 rename `.bak` → move tmp → 成功再删 bak；`q()` 做 YAML 转义。灾难预防 / **约 2 小时**。

### 6. HALF_OPEN 永远显示不出来 + 合成 500ms 速度样本
- **证据**：`...\policy\PolicyService.java:950` `er.coolDownUntil > now ? (now >= er.coolDownUntil ? "HALF_OPEN" : "OPEN") : "CLOSED"` —— 内层条件在外层真分支里恒假；`...\gateway\GatewayController.java:488` 与 `...\gateway\AnthropicController.java:442` 的 `ttftMs == null ? 500 : ttftMs` 向 EWMA/中位数注入合成样本（非流式成功路径密集）。

## 二、功能增强：对"快·准·省·少早停"有直接收益

### 9. 上游错误语义分类器进路由层（让"文字型限流"也触发冷却/降权）
- **证据**：`...\admin\AdminController.java:1031-1059` 已有 24 条错误模式表 `translateError`，**只用于界面展示**；`...\policy\PolicyService.java:775-809` 限流判定纯按 HTTP 状态码（429/401-403），仅 `insufficient_quota` 走长冷却。
- **日志实证**（`...\logs\gateway.log`，09-16~18）：`tpm/rpm limit 429003 ×65`、`code 1305 访问量过大 ×22`、`concurrency limit (64) ×10`、`code 50609 ×2` —— 只要不以 HTTP 429 出现就完全不触发冷却，下个请求继续撞同一面墙。
- **修法**：抽 `UpstreamErrorClassifier`（RATE_LIMIT / QUOTA / MODEL_NOT_SUPPORTED / SERVER_BUSY / …），`ForwardResult` 带枚举，`recordFailure` 按语义定冷却时长；`MODEL_NOT_SUPPORTED`（日志 ×12）短期豁免该家该模型。纯增量判定、兜底走现有分支。**约 1 天，收益高**。

### 10. 压缩调用记账 + request_log 加 `http_status`/`error_class` 两列
- **证据**：`...\forward\ContextCompressor.java:361-457` `callCompressor` 无 `recordSuccess`/`addUsage`/`logRequest` → 压缩烧的 token 不进 usage_daily、不进日预算、日志页隐形（实测 84 次成功压缩零记账）；`...\store\Database.java:51-69` 无 `http_status` 列，FAILED 无法区分 429/400/500（`响应头超时 ×55`、`1305 ×22` 全部只落 `status=FAILED`）。
- **修法**：压缩走 `logRequest(client=gw-compress)` 带真实 provider/model/tokens；`ALTER TABLE` 两列（沿用 `Database.java:113` 的 `columnExists` 迁移守卫）。与 09-19 设计文档的 `trace_id` 是**同一次 schema 迁移**，应合并做。**约 0.5-1 天**。

### 11. 流式请求的并发上限形同虚设
- **证据**：`...\gateway\GatewayController.java:162` `acquireInflight` 与 `:178` `releaseInflight` 只包住 `hedgedExecutor.execute`；数据排空在 `:217 → streamToClient`（最长 120s）不占额度，Anthropic 端同构。日志实证 `concurrency limit (64) ×10` 恰在流式阶段被击穿。
- **修法**：STREAM 的 inflight 释放延后到 `streamToClient` 结束。**约 1 小时**。

### 12. 滚动压缩缓存 key 只按 client → 多会话必然打偏
- **证据**：`...\forward\ContextCompressor.java:166-168` `rolling.get(cl)`、`:228` put——key 只有 client；Claude Code 子代理 / rewind / 同工具多窗口互相覆盖前缀哈希 → 走 `:420` `budget=min(max(channelBudgetMs,120_000),120_000)`、`Long.MAX_VALUE` 总预算的全量链（串行遍历全部候选，最坏数分钟）。另 `:460-481` `hashOf` 每次对整段历史 O(n) 序列化。
- **日志实证**：`incremental-ok 72` vs `full-ok 12 + full-ok-shrunk 2`——单会话时增量有效，桶粒度是其恶化的唯一路径。
- **修法**：key 改 `client + 会话指纹`（首条 system 哈希或消息数单调性校验）；`hashOf` 只哈希尾锚点增量。**约 0.5 天**。

### 13. 探测轮加"空闲门控"
- **证据**：`...\probe\ProbeScheduler.java:107-134` runRound 无在途请求检查；日志实证 09-16~18 `client=probe 622` 行 vs 真实流量 235 行（**约 72% 日志量在抢同一份免费 RPM**）；`:169-170` 探测成功不落 ttft/total，探测延迟历史不可回溯。
- **修法**：在途计数 >0 则跳过/延后本轮；探测行补记 ttft。与 excludeFromProbe（已上线）正交。**约 1 小时**。

### 14. 前端：系统页运行时表不刷新 + 数据请求失败被静默吞
- **证据**：`index.html:1176` 轮询条件写死 `#tab-providers` 可见；`switchTab` 的 sys 分支（`:333`）不调 `loadAll()` → 盯熔断/EWMA 时画面永不更新；`loadUsage()`(`:899`)、`loadLogs()`(`:971`) 无 try/catch，且 `/api/usage` 异常时后端返回 **200** + `{error}`（`AdminController.java:671`），前端不读 `d.error` → 后端 SQL 错被翻译成人眼可见的"暂无数据"；`#discBtn/#lsBtn` 初始"读取中"，启动那一瞬失败则永久卡住（`:1110/:1149` catch 为空）。
- **修法**：sys 分支补 `loadAll()`、轮询纳入 sys 页；fetch 失败在表格区显示红字错误 + 按钮重试。**约 1 小时**。

### 15. 前端：早停排障证据面补齐（后端已返回、界面 0 处渲染）
- **证据**：
  - `/api/logs` 每行含 `compress`(`AdminController.java:1021`) 与 `profile`(`:1017`)，`index.html` 中出现 **0 次**——compressTag 的设计注释（`ContextCompressor.java:82-83`）明写"供管理页排查"，恰是判断"早停是否压缩引起"的唯一落库证据；
  - `runtimeView()` 的 `earlyStopSuspects`（`PolicyService.java:969-981`，注释即"诊断透明"）前端 0 处渲染；
  - 还漏：`recentTtftMedian`(`:947`)、`coolDownUntil` 倒计时（熔断标签 `index.html:469` 是静态的）、`lastRateLimitedAt`；
  - `/api/client-queue`(`AdminController.java:1110-1115`) 是端点齐全、界面零入口的孤儿诊断接口。
- **修法**：日志行点击展开详情行（零后端改动）；系统页加"早停惩罚中"子表 + 熔断倒计时 + 并发队列只读卡。**约半天，直接补全"为什么早停/为什么选这家"的界面链路**。

### 16. 前端：日志分页/排序/CSV 导出 + 用量→日志一键钻取
- **证据**：后端支持 `offset`、`limit≤500`（`AdminController.java:973,1002`），前端硬编码 `{limit:100}` 从不传 offset（`index.html:972`）→ 过滤出 2000 条失败只能看最新 100 条；表头不可排序；无导出；用量表失败徽标（`index.html:943`）不可点，而日志页 `providersIn/realModelsIn/statusIn` 全支持——从"openrouter 失败 37"到"看这 37 条"要手动勾 3 个下拉。

## 四、执行边界（并入自评审文档，施工时必须遵守）

1. **#13 空闲门控必须带最大延迟兜底**：纯"在途>0 就跳过"会让持续流量时段探测永不跑。要求延后累计 **>10 分钟强制执行一轮**。（精确化：半开恢复其实有两个入口——`ProbeScheduler:166` 与真实请求 `GatewayController:161`，冷却到期后候选本来可被真实流量验证；探测的真正价值是**没有流量流向的模型的唯一验证通道**。另：兜底轮对 `excludeFromProbe` 模型只做半开验证、不做常规刷新，别把豁免额度烧了。）
2. **#10 压缩记账是行为变化不是纯观测**：补记后压缩 token 开始占日预算，免费档可用额度变少。上线后若"日预算提前耗尽"由压缩引起，属记账归位而非新 bug；上线当天对照 `/api/usage` 的 client 分桶确认量级。
3. **#11 流式占并发后行为变严**：长流（最长 120s）期间占住并发额度，`concurrency limit` 会拒绝更多新请求。上线当天某家"突然开始排并发/报 concFull"是预期，不是回归。
4. **#1 修复当天速度样本会突变**：Anthropic 端 TTFT 从"整段流时长"变回真首字后，相关模型 EWMA/中位数会**明显变快**，分摊抽签与"极慢踢出"结论随之移动——这是修复生效。上线时间记入运行日志，当天看到跳变直接对照，不要重新排查。
5. **#12 会话指纹只用 system 哈希不够**：Claude Code 子代理/多窗口/rewind 的 system 完全相同，分不开。指纹取 **「首条 system + 前 2 条 user 内容」组合哈希**，并保留消息数单调性校验兜底（消息数变少且哈希不匹配 → 视为新会话走全量压）。

## 六、与《功能扩展设计（压缩自检/toolWeak学习/trace）》的重叠与衔接

- **trace_id（设计文档三）** 与本清单 **#10**：同一次 `ALTER TABLE` 迁移，建议 `trace_id + http_status + error_class` 三列一次做完，避免两次动 schema。
- **压缩自检（设计文档一）** 与本清单 **#10**：压缩调用落 `client=gw-compress` 的 request_log 后，"压缩现在好不好使"在日志页即日常可见；一键体检仍值得做（主动回归验证），但记账先行、成本低收益早。
- **toolWeak 学习（设计文档二）** 与本清单 **#1/#3**：建议条件 `toolsRequestsSeen≥20 && 从未回 tool_calls` 必须在 #1/#3 修复**之后**才有意义——否则"没回 tool_calls"可能其实是转换 bug 或收尾 bug 的假象；且样本应只统计 `status=OK` 的完成请求，避免把"慢/死"误学成"弱工具"。
- 自检第 3 类检查（每 free 模型带 trivial 工具的真实请求）会烧真实额度，应对 `excludeFromProbe` 已豁免的模型**跳过或降频**（如每周一次），否则 openrouter/free 的每日硬顶会被体检吃掉一块。
