## 0. 一句话理解本系统

**在零成本（免费模型）优先的前提下，用一套自学习的路由大脑，让「快（低延迟、不断流）、好（结果可靠、任务不中断）、省（几乎不花钱）」三个目标同时达成**——而不是像商用网关那样靠付费模型堆性能。

核心矛盾：免费模型的**限额极小**（每分钟 N 次、每天有限、并发有限），一旦流量集中就被 429 打爆，任务就断。本系统的所有工作在根本上都围绕一件事展开——**如何在免费池里把「快/好/省」榨到极致，同时用付费极低频兜底保证「永不断开」**。

## 1. 「快」：延迟与吞吐的极致优化

"快"不是简单选最快的模型，而是在**不知道哪家真的快**的前提下（免费模型速度波动大），让系统自己感知并动态择优。

### 1.1 评分驱动的动态选路（选得对，才快）

每条请求先用 `RouterService` 把 model 名解析成候选池（组名→候选、点名单、直接名匹配），再用 `PolicyService.rank()` 打分排序：

```
得分 = 优先级P × 健康度H × 首字速度S × 吞吐T × 费用C × 语义匹配K × 限流恢复R × 限流压力L
```

各因子含义：
- **P 优先级**：管理员配置，量级刻意收窄（`40/(1+priority*5)`），让速度/健康在同优先级邻域内有实际话语权，而不是纯按优先级排队。
- **S 首字速度**：每家的 EWMA TTFT（首字延迟指数滑动平均），200ms 即满分。**这是"快"的核心传感器**——系统实时感知谁真的快。
- **T 吞吐**：EWMA 出 token 速率（tok/s），长回复场景快模型胜出。
- **H 健康**：连续失败越多分越低，冷却≈0。
- **K 语义匹配**：请求类别（code/doc/…）命中所擅长类别的模型 ×1.8——同类里选擅长的，通常也更快更准。
- **C 费用**：free=1.0 / premium=0.1，十倍压制——免费优先的内建哲学。
- **R 限流恢复**：刚 429 过的渠道即使冷却到期也短期降权（见 3.2）。
- **L 限流压力**：当前窗口用量接近学到的限流上限就降权（见 2.2/3.3）。

### 1.2 实时速度感知：EWMA 采样
- 每家每模型维护 `ewmaTtftMs`（首字延迟）和 `ewmaTokensPerSec`（吞吐），成功请求持续更新。
- **三条防污染规则**保证样本不被"骗"：
  1. 输入 >10K token 的大请求 TTFT **不进** EWMA（预填充开销 ≠ 模型真实速度）；
  2. 无样本时免费给乐观默认 0.9、付费给保守 0.5（未知的付费模型绝不排到有真实样本的免费前面——修复过"付费反超"事故）；
  3. 无样本时吞吐同理免费 1.0/low 0.9/premium 0.5。

### 1.3 对冲请求（Hedged Requests）—— 慢首字的最优解
- 默认 `hedgeDelayMs=2500`：主选先发，若 **2.5s 内没出首字**，并发一个次选竞速，谁先非失败谁胜，输家掐断连接（几乎不产生 token）。
- 只在流式、且输入 token ≤10K（对冲双发=双倍限额，大请求禁用）时生效。
- 实测：慢首字(20s)的主选 + 正常备选 → 总 2.8s 拿到首字；主选健康时零对冲零额外请求。

### 1.4 低频定时探测（ProbeScheduler）—— 让"快"不因空闲而变盲
- 每 30 分钟（`probeIntervalMinutes`）对**免费模型**发 max_tokens=8 的探测，刷新 EWMA 样本 + 熔断提前恢复。
- 空闲模型（如 agnes、openrouter）因此始终有新鲜速度样本，评分回到实时——**"快"不依赖真实流量恰好来过这家**。
- 只探免费（付费绝不为探测花钱）。

### 1.5 上下文压缩 —— 大请求变快、变省
- 输入 > `contextCompressThresholdTokens`（默认 100k）时，网关先把历史压成摘要再转发（滚动缓存，前缀命中只压增量，实测增量 6ms）。
- 既让大上下文请求更快出结果，也省 token（见 2.4）。

## 2. 「好」：结果可靠、任务绝不中断

"好"在这个系统的语境下有两层：**返回的结果正确可用**（不为省而牺牲质量），和**任务永不因网关原因而断开**。

### 2.1 铁律：风险阶段之前先解决可靠性
"永不给工具报错" 是最早确立的红线，贯穿所有选路：
- `rank()` **永不返回空**：全部候选不可用时放行最佳兜底（预算/并发耗尽的最高分、或连续失败最少者）强制探测，由上游/超时给出真实结果，而非网关直接拒绝。
- 未知模型名自动回落 `free-fast` 组——工具侧只配一个名字就不会失效。
- `maxAttempts` 穷尽全部候选（上限 6），保证有结果。

### 2.2 上下文 window 预过滤 —— 不在接不住的模型上白烧
- 判断请求输入 token 估算，超过模型 `contextWindow×1.1` 的直接出局——避免 152K 请求打 128K 模型白烧 attempt、还浪费大量免费额度。
- 实测：150K 请求直接落容量够的模型，不再把 zhipu 三连 400 白烧。

### 2.3 调度正确性的三层治理
- **熔断状态机**（连续失败达阈值 → OPEN 冷却 → 半开探测 → 恢复），防止坏模型反复被打。
- **429 分级冷却**：瞬时限流 30s（`rateLimitCooldownMs`）；配额耗尽 600s 长冷却（`quotaCooldownMs`）——不再每个请求都撞墙。
- **多 Key 严格轮转**：同模型多把 Key 按最近使用时间严格交替（一号限速不拖累二号），别家账号没在担流量就让它接。

### 2.4 上下文自动压缩 —— 靠省实现"好"（结果不因超限而失效）
- 大上下文会被上游拒绝或烧光预算，压缩让请求**能打完**（结果完整）而不是被截断——这是"好"的一部分。
- 压缩永不成为请求失败原因：压缩失败/未配模型一律原样转发。

### 2.5 付费兜底 —— 最终意义上的"任务不断开"
- 当**所有免费候选都在冷却/限流**时，`pickGuaranteed()` 优先放行**一个不在限流压力下的付费模型**，作为最后一道保证返回（日志：`[限流兜底] 免费全挂，放行付费 ... 保证任务不断开`）。
- **付费频率天然低**：只在免费全员限流时触发；常态免费占满额度。
- 这是用户明确的目标：**付费就是为了不让任务断开**，而免费优先保证"省"不失衡。

### 2.6 协议与兼容性
- OpenAI 原生 + Anthropic 协议自动转换（Claude Code 用 `/v1/messages`、Codex/ZCode 用 `/v1/chat/completions`）。
- 工具调用多轮消息序自动重排（孤儿 tool 转 user、缺结果补空 tool），修复过 "tool message must follow an assistant message" 的 400。
- 按渠道注入"关思考"参数（不同家开关不同：thinking disabled / chat_template_kwargs / 不注入），避免推理模型把 max_tokens 全烧在思考上导致空回复。

## 3. 「省」：几乎零成本，且越用越省

"省"是这套系统的**存在意义**——用免费模型提供接近付费的体验，且成本不随时间膨胀。

### 3.1 免费优先 + 付费低限兜底，砍掉一切冗余调用
- 费用因子十倍压制（free=1.0→premium=0.1），评分天然偏好免费。
- **目录只信手工配置**（默认关自动发现），不拉回一堆不可调用的模型条目。
- **探测只对免费模型**，付费绝不为探测花钱。
- **对冲只在流式且小输入**时开，避免双发双倍限额。
- 压缩模型默认 `free-fast`（免费全家桶自动轮转，附费用守卫：named 组=freeOnly，点名 provider/model 才允许付费）。

### 3.2 避免 "冷却了等于没冷却" 的隐性浪费
- 429 冷却 30s 但高频工具（claude-code 0.5s 一发）不等冷却，导致同一家反复撞墙烧 attempt。
- **限流恢复因子 R**：刚 429 过的渠道在「冷却 + 半段恢复宽限」期间降权（0.35→1.0 回升），把连发流量送去别家，而不是同一免费家反复白烧。

### 3.3 自适应限流学习 —— 越用越省（省的关键创新）
- 不猜每家限流规则（有的每分钟 8 次、有的按分钟 token、有的按天、有的限并发），而是**在 429 触发时刻把当时窗口用量采样为该家的经验上限**。
- 经验上限**只向下收敛**（更保守），每次 429 强化置信度。
- 路由前 `ratePressure()` 返回当前用量/经验上限，评分乘 `L` 因子（压力满→×0.2）——**主动绕开快达上限的家，转向还有余量的家**，不等 429 才冷却。
- 效果：流量在免费池里自动均匀分摊，单家不再被锤爆；**同样的免费额度支撑更多请求**，这就是"越用越省"。诊断端点 `GET /api/rate-limit-learn` 实时可查学到上限。

### 3.4 同源并发队列 —— 省的前提是"别自己打爆自己"
- 同一工具(client)并发 >2（`clientMaxConcurrency`）的请求排队等上一个完成（含流式），默认 30s 超时放行兜底。
- 这是省的关键前提：**免费额度小，最怕同一工具的突发并发一次性把某家顶爆**。队列把同源连发串行化，从根上避免 429 风暴，让免费渠道不被白白耗尽。

### 3.5 费用档与预算治理
- 条目/提供商/Key 三级当日 token 预算，触发即冷却，不白烧。
- 语义路由、查上游价格自动定档（免费标绿、付费标黄）——成本透明。

## 4. 「快好省」如何协同：请求的完整旅程

以 claude-code 一个工具调用请求为例，看三层如何串起来：

1. **省（入口）**：同源并发队列把关 → 并发 >2 先排队，不自己打爆。
2. **好（路由）**：解析 free-fast 组 → 按 `P×H×S×T×C×K×R×L` 打分 → 自动选免费余量足、速度好的家（R/L 保证刚限流的家先让位，换家不乱撞）。
3. **快（转发）**：流式及时出首字；慢就 2.5s 后对冲竞速；超时换家（already 出字不切换不误伤）。
4. **好（上下文）**：输入超限先压缩，保证能打完。
5. **省（持久化）**：每次成功/429 都在学习窗口记账、学限流上限 → **下一次选路更聪明、更省**。
6. **好（兜底）**：万一免费全挂 → 付费极低频兜底，任务绝不断开。

> 一句话：**入口靠队列控并发（别浪费），中途靠自学习路由选最划算（最大化利用），末尾靠付费兜底保不中断（永不失败）。** 三者缺一不可，共同构成 "快好省" 的核心。

## 6. 这套设计的取舍与边界

- **为什么不是纯免费堆叠**：免费限额真的极小，高峰期（大量工具连发）必然触发 429。取舍是：**免费池里用尽一切办法（分流/探测/避让/队列）扩大吞吐，付费只在最终兜底**——频率低到系统仍"几乎免费"。
- **为什么不用传统 IDP（限流令牌桶）**：传统网关限流是"按我设定的规则限"，本系统是**按学到的各家真实限制来自适应避让**——不需要人工维护每家的 429 规则，符合"越用越聪明、几乎零运维"。
- **已知边界**：自适应学习的上限收敛默认偏向保守（宁少用不多撞）；若某家实际限额更宽，可通过调低保守系数让它更大胆。
